# Sierx interface and theme contract

Sierx uses one semantic interface contract with interchangeable appearances. The
contract covers the current backlog, item detail, and sign-in screens, and is
the required foundation for the planned Kanban, hierarchy, and forecasting
surfaces. Components describe what content does; theme tokens and optional
theme CSS describe how it looks. A theme must not change workflow meaning,
keyboard behavior, or available actions.

## Appearance catalog

All 23 visual directions in the supplied design package remain available:

`swiss`, `quiet`, `ledger`, `commander`, `platinum`, `blueprint`, `eink`,
`eink-dark`, `ticker`, `plain`, `brutal`, `civic`, `dusk`, `cockpit`, `chart`,
`appliance`, `redlight`, `celadon`, `riso`, `vellum`, `kraft`, `indigo`, and
`indexcard`.

The package's 13 third-party font families are all marked OFL-1.1. None of
their font files or declarations are included in Sierx. The themes instead use
operating-system font stacks and, where useful, Sierx Mono and Sierx Symbols,
which are compiled from included source under the repository's Apache-2.0
license. Existing preference values remain accepted; the browser maps `light`
to `quiet`, `dark` to `dusk`, and the old high-contrast values to the matching
e-ink appearances.

## Shared component vocabulary

Use the following classes and data attributes for new interface surfaces:

| Purpose | Contract |
|---|---|
| Application frame and navigation | `.sx-app`, `.sx-top`, `.sx-brand`, `.sx-tab`, `.sx-side`, `.sx-main`, `.sx-foot` |
| Page heading and query | `.sx-main-h`, `.sx-main-title`, `.sx-main-sub`, `.sx-query`, `.sx-field`, `.sx-control` |
| Backlog/list | `.sx-list`, `.sx-row`, `.sx-key`, `.sx-type`, `.sx-row-title`, `.sx-status` |
| Board | `.sx-board`, `.sx-col`, `.sx-col-h`, `.sx-cards`, `.sx-card`, `.sx-card-meta` |
| Hierarchy and rollups | `.sx-tree`, `.sx-node`, `.sx-node-row`, `.sx-twisty`, `.sx-roll` |
| Item document | `.sx-doc`, `.sx-doc-head`, `.sx-doc-title`, `.sx-fields`, `.sx-md`, `.sx-comment`, `.sx-activity` |
| Flow and forecast | `.sx-stats`, `.sx-stat`, `.sx-forecast`, `.sx-forecast-chart` |

Use `data-cat` for the stable status categories `open`, `active`, `done`, and
`cancelled`, and `data-type` for the item's semantic type. Status always has a
text label and glyph as well as color. Selection, blocked state, and forecast
uncertainty also have a non-color cue. Focus remains visible in every theme.

All themes share the same color tokens, type scale, spacing, density, borders,
focus, and status contract. A theme may tune those tokens or apply a local CSS
refinement to the shared class vocabulary. Keep refinements in
`web/design/css/themes/`; do not add component-specific theme forks. Colors are
declared in `web/design/tokens/`, generated by
`web/design/tools/build-tokens.mjs`, and contrast-checked during every web
build.

## Planned surface use

- **Current workspace:** the backlog list uses the shared row vocabulary;
  item details use document, field, comment, and hierarchy elements; login uses
  the same controls and focus rules.
- **Phase 3 Kanban:** columns are labelled lists, cards carry the same key,
  type, status, blocked, and selection semantics as backlog rows. Each of the
  23 appearances must render the board and its keyboard/context-menu flows.
- **Phase 5 hierarchy:** arbitrary-depth nodes use the tree vocabulary; status
  and progress rollups are text plus a bar, and relationship overlays remain
  distinguishable without color. Keep theme testing in the depth-six and
  critical-path acceptance fixtures.
- **Phase 6 Ticker forecasting:** the forecast view uses shared stats, chart,
  confidence-band, observed-series, and target-series styles. It must show the
  observed sample and uncertainty, state when the sample gate is not met, and
  remain legible in every appearance. Themes do not change forecast data or
  statistical rules.

These are design requirements for the existing phase gates, not authorization
to implement future-phase functionality before its entry criteria are met.

## Offline and dependency rule

Theme, token, CSS, and Sierx font generation use local repository inputs and
Node built-ins. The web build checks generated token files, rebuilds the Sierx
font faces for byte-for-byte parity, and rejects remote CSS/font references.
The design package adds no npm dependency and never downloads a font. The
frontend dependency graph remains pinned in `web/package-lock.json`; a clean
offline source build needs the locked packages already staged in `node_modules`
or in the local npm cache. The production app embeds its built assets, so
runtime delivery does not need a font service, CDN, or internet connection.
